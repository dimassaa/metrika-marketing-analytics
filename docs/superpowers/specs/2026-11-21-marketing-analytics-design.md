# «Метрика» — web-приложение оценки эффективности маркетинговых каналов

Дата: 2026-11-21
Статус: черновик на утверждение
Курсовой проект по дисциплине «Проектирование и разработка web-приложений» (БГУИР, кафедра ЭИ)

## 1. Зачем это

Маркетолог в небольшой белорусской компании сводит расходы на каналы в Excel, а выручку — в админке магазина.
Чтобы понять, окупается ли Instagram, он вручную делит одно на другое, путается в когортах и в итоге решает
«на глаз». «Метрика» собирает расходы, заказы и касания в одну модель и отвечает на три вопроса:

1. Сколько стоит привлечь клиента из каждого канала (CAC)?
2. Сколько он приносит за год (LTV)?
3. Что вернёт каждый вложенный рубль (ROMI) и куда переложить бюджет, чтобы стало лучше?

Продукт — не «дашборд ради дашборда». Ценность в расчётах: когортный LTV, три модели атрибуции, кривые насыщения
и оптимизация бюджета. Графики — способ это показать, а не самоцель.

### Пользователи

| Роль | Кто это | Что делает |
|---|---|---|
| Администратор | владелец/руководитель | управляет пользователями, целями, видит аудит, может всё |
| Маркетолог-аналитик | штатный маркетолог | ведёт каналы, кампании, импортирует данные, строит сценарии |
| Наблюдатель | собственник, бухгалтер | только смотрит дашборды и отчёты, ничего не меняет |

Демо-компания: интернет-магазин кофе «Зёрна» (Минск), 8 каналов, 14 месяцев данных в BYN.

## 3. Границы

**Цели**
- корректные, проверяемые расчёты CAC/LTV/ROMI на уровне промышленного кода;
- интерфейс, который не стыдно показать: спокойная аналитика, читаемые графики, ноль визуального шума;
- воспроизводимый демо-стенд: `docker compose up` или `npm run dev` + локальный PostgreSQL;
- прозрачность: у каждой цифры есть формула, период и источник.

**Не цели**
- реальные интеграции с рекламными API (Google/Meta/TikTok) — только CSV-импорт;
- мультиарендность, биллинг, мобильное приложение, e-mail-рассылки;
- прогнозирование ML-моделями, произвольные формулы, BI-конструктор;
- тёмная тема в MVP (токены заложены, но не включена);
- пояснительная записка и диаграммы — отдельный этап после кода.

**Анти-цели (провал, даже если «работает»)**
- цифры на экране нельзя пересчитать вручную по формуле из интерфейса;
- дашборд из 12 разноцветных графиков без иерархии;
- «красиво, но пусто»: нет данных, нет инсайта, нет рекомендации;
- бизнес-логика размазана по шаблонам и React-компонентам;
- приложение требует TypeScript, сборки CSS или облачных сервисов для запуска.

## 4. Стек и обоснование

| Слой | Решение | Почему именно так |
|---|---|---|
| Runtime | Node.js 24 LTS (`>=22`), ESM | требование бланка, актуальный LTS |
| HTTP | Express 5 | требование бланка, зрелый роутинг и middleware |
| Шаблоны | EJS 3 | серверный рендер, гиперссылки, SEO, минимум магии |
| БД | PostgreSQL 18, `pg` + SQL-миграции | реляционная модель, FK/CHECK, оконные функции для когорт |
| Деньги | целые копейки (`BIGINT`) | никакой плавающей точки в финансах |
| Валидация | Zod | одна схема для форм, API и импорта |
| Auth | `express-session` + `connect-pg-simple`, argon2id (`@node-rs/argon2`) | серверные сессии, отзыв, роли; prebuilt-бинарь без node-gyp под Windows |
| Безопасность | helmet + CSP, CSRF double-submit, rate-limit, RBAC | закрывает §3.3.4 бланка |
| Логи | pino + pino-http, request-id | структурные логи, трассировка запроса |
| Клиент | React 19 (острова) + Vite 7 (только сборка) | интерактив там, где он нужен; SSR и MVC сохраняются |
| Графики | Recharts 3 | SVG, точная стилизация под дизайн-токены, доступные тултипы |
| Тесты | Vitest + Supertest, agent-browser для e2e | быстрые юниты формул, интеграция API, реальные клики |
| Деплой | Dockerfile + compose (app + db), локальный PG | требование Windows 10, воспроизводимость |

**Решение по React (осознанное).** Бланк требует MVC/MVP, поэтому чистый SPA на React не подходит: он превращает
Express в JSON-заглушку и ломает серверный рендер. Используем **острова**: каждая страница — EJS-шаблон, который
рендерит контроллер; внутри — React-остров с начальными данными из серверного view-model и JSON API для действий.
React отвечает за графики, фильтры, симулятор и таблицы; навигация — обычные ссылки. Это одновременно MVC,
прогрессивное улучшение и современный React. Если нужен именно SPA — это решение надо переиграть до старта.

## 5. Архитектура

```
Браузер
  ├─ HTML (EJS, SSR) ───────────────┐
  └─ остров (React) ── fetch ──┐    │
                               ▼    ▼
                        Express 5 (MVC)
                        routes → controllers
                                   │
                              services (бизнес-логика, чистые функции)
                                   │
                            repositories (SQL, pg Pool)
                                   │
                             PostgreSQL 18
```

Правила слоёв:
- **controller** — разбирает HTTP, валидирует вход, вызывает сервис, выбирает шаблон/статус. Без SQL и формул.
- **service** — бизнес-логика и математика. Не знает про `req`/`res`. Принимает простые объекты, возвращает view-model.
- **repository** — только SQL и маппинг строк. Никаких решений «что считать».
- **view** — только отображение. Формулы в шаблонах и React запрещены; форматирование — через общие хелперы.
- **React-остров** — получает начальные данные в `data-props` (JSON, экранированный), дальше — `/api/v1/*`.

Сборка клиента: Vite multi-entry (`client/entries/*.jsx`) → `public/assets/` с манифестом; Express читает манифест и
подставляет хешированные файлы. CSS в React не импортируется — только классы из `app.css`.

Деньги — `BIGINT` в копейках, суффикс `_cents`. Даты событий — `timestamptz` (UTC), календарные — `date`.
Отображение — Europe/Minsk (UTC+3, без перехода на летнее время).

| Таблица | Ключевые поля | Связи/ограничения |
|---|---|---|
| `users` | email, password_hash, full_name, role, is_active, last_login_at | UNIQUE(email), CHECK(role in admin/analyst/viewer) |
| `sessions` | sid, sess, expire | connect-pg-simple |
| `channels` | code, name, kind, is_active, target_cac_cents, target_romi_pct | UNIQUE(code) |
| `campaigns` | channel_id, name, status, started_on, ended_on, budget_cents | FK channel, CHECK(status) |
| `daily_stats` | campaign_id, stat_date, impressions, clicks, leads, spend_cents | UNIQUE(campaign_id, stat_date), FK |
| `customers` | external_id, first_channel_id, first_campaign_id, first_order_at, acquired_at | UNIQUE(external_id), FK channels |
| `touchpoints` | customer_id, channel_id, campaign_id, occurred_at, kind | FK, индекс (customer_id, occurred_at) |
| `orders` | external_id, customer_id, campaign_id, occurred_at, revenue_cents, margin_cents | UNIQUE(external_id), FK, CHECK(revenue>=0), индекс (occurred_at) |
| `goals` | metric, channel_id NULL, target_value, period_start, period_end | CHECK(metric) |
| `alerts` | channel_id, rule, severity, period_start, value, threshold, status | UNIQUE(channel_id, rule, period_start) |

## 10. Безопасность и данные

- Пароли — argon2id, политика ≥10 символов, блокировка после 5 неудач на 15 минут (rate-limit + счётчик).
- Сессии: httpOnly, sameSite=lax, secure в production, regenerate при входе, TTL 8 часов.
- CSRF: double-submit токен для всех POST/PUT/PATCH/DELETE, включая fetch-запросы островов.
- RBAC: middleware на каждый маршрут, проверка владельца для сценариев; аудит значимых действий.
- SQL только параметризованный; вывод — через `<%= %>`/React (без `innerHTML`); CSP без `unsafe-inline` для скриптов.
- Секреты — `.env`, `.env.example` без значений; валидация env при старте, падение при отсутствии.
- Бэкапы: `pg_dump -Fc` → AES-256-GCM (`scripts/backup.js`), retention 7 дней, restore-скрипт и проверка.
- TLS: инструкция для reverse-proxy (Caddy/nginx) в `docs/deployment.md`; в Docker — HTTP внутри, TLS снаружи.
- Импорт: лимит 2 МБ и 10 000 строк, проверка MIME/расширения, отчёт ошибок без записи мусора.

## 11. Наблюдаемость и производительность

- Структурные логи pino: request-id, user-id, route, latency, status; ошибки — с контекстом.
- `/health` — проверка БД и версии; используется Docker healthcheck.
- Метрики запросов в логах (latency, slow query > 200 ms — предупреждение).
- N+1 запрещены: списки агрегируются SQL, проверка на интеграционных тестах по числу запросов.
- Пагинация по 25/50, индексы под фильтры, `EXPLAIN` для трёх самых тяжёлых запросов перед сдачей.
- Кэш: `Cache-Control` для статики (immutable), данные дашборда — без кэша в MVP (честность важнее).

## 12. Тестирование

- Юнит: все формулы (CAC, LTV, ROMI, payback, ranking, saturation, optimizer, alerts) на ручных фикстурах,
  включая деление на ноль и пустые периоды.
- Интеграция: вход/выход, RBAC-матрица, CSRF, импорт (валидный/битый/дубли), API-контракты, миграции с нуля.
- E2E через agent-browser: вход каждой ролью, дашборд, создание канала, импорт, сценарий, экспорт, 403/404.
- Сид проверяется инвариантами (суммы, FK, количество когорт).
- Тесты запускаются параллельно; регрессия на каждый найденный баг.

## 13. Развёртывание

- Локально: Node 24, PostgreSQL 18, `npm ci`, `.env`, `npm run migrate && npm run seed`, `npm run build`, `npm start`.
- Docker: multi-stage (build client → runtime), compose с `db` и `app`, healthcheck, volume, `.env.example`.
- Windows 10: инструкция с установкой Node/PostgreSQL, созданием БД, переменными, запуском, бэкапом через
  Планировщик заданий. Docker Desktop — альтернативный путь.

  (демо-стенд, не production).

## 14. Этапы

1. **M1 Фундамент** — репозиторий, конфиг, миграции, сид, дизайн-токены, layout, лендинг, авторизация.
2. **M2 Данные** — каналы/кампании, импорт CSV, цели, аудит, пользователи.

## 15. Решения, принятые без тебя (проверь при чтении)

1. React — островами внутри Express MVC, не SPA. Причина: требование MVC и SSR/SEO.
2. CSS — рукописный один файл, без Tailwind. Причина: буквальное «одна каскадная таблица стилей».
3. Деньги — копейки в `BIGINT`, не `NUMERIC`/float.
4. Сессии в PostgreSQL, не JWT. Причина: отзыв доступа и меньше самодельной криптографии.
5. Атрибуция по умолчанию last-touch, CAC — по first-touch (канал привлечения).
6. Семантические цвета статусов добавлены к палитре Seline (иначе здоровье каналов нечитаемо); используются
   только как индикаторы, не как акцент.
7. Бренд «Метрика», демо-компания «Зёрна», данные вымышленные, но правдоподобные для РБ.
8. ПЗ и диаграммы не входят в этап кода.
