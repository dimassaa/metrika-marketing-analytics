# Спецификация метрик: CAC, LTV, ROMI и производные

Дата: 2026-11-21
Область: бизнес-логика `src/services/*`, тесты `tests/unit/*`
Валюта: BYN, хранение в копейках (`BIGINT`, суффикс `_cents`). В формулах `cents` сокращается до `c`.
Время: хранение UTC, периоды и когорты — Europe/Minsk (UTC+3, без DST).

## 0. Общие соглашения

- Период `[from, to]` — включительно по календарным датам Minsk.
- «Новый клиент» — клиент, у которого `first_order_at` попадает в период. Клиент считается новым один раз, глобально.
- Канал привлечения клиента — `customers.first_channel_id` (first-touch навсегда), фиксируется при первом заказе.
- Расход канала — сумма `daily_stats.spend_cents` кампаний канала за период.
- Все деления проверяют ноль: результат `null`, в UI — «—» и статус «недостаточно данных». `NaN`/`Infinity`
  не должны покидать сервис.
- Округление: промежуточные значения не округляются; деньги округляются до копейки (half-up) в момент возврата,
  проценты — до 2 знаков, коэффициенты — до 3.
- Изменение в процентах: `(new - old) / abs(old) * 100`, при `old = 0` → `null`.

### 0.1. Отчётная дата (data anchor)

Демо-стенд может открываться позже, чем заканчиваются данные. Поэтому «сегодня» для расчётов — не системные часы,
а **последняя дата с данными**: `anchor = MAX(daily_stats.stat_date)` (fallback — текущая дата Minsk).
Все периоды по умолчанию (30/90/180 дней), окна алертов и горизонты когорт считаются от `anchor`.
В интерфейсе всегда видно: «Данные по 20.11.2026». Это же значение возвращает `/api/v1/reference`.

Сид генерирует данные по вчерашний день относительно запуска, поэтому повторный `npm run seed` освежает стенд.
Тесты фиксируют `anchor` явно, чтобы не зависеть от календаря.

## 1. CAC (BO-01)

```
CAC_channel = spend_channel / new_customers_channel
CAC_blended = Σ spend_all / Σ new_customers_all
CAC_campaign = spend_campaign / new_customers_campaign
```

`new_customers_channel` — число клиентов с `first_channel_id = channel` и `first_order_at ∈ [from, to]`.
`new_customers_campaign` — аналогично по `first_campaign_id`.

Краевые случаи:
- `new_customers = 0` → `cac = null`, `status = "no_data"`.
- `spend = 0`, клиенты есть → `cac = 0`, помечается как «бесплатный канал» (SEO, email в демо).
- CAC никогда не смешивает расходы одного канала с клиентами другого.

Пример: Instagram, октябрь: расход 4 200,00 BYN, 84 новых клиента → CAC = 50,00 BYN.

## 2. LTV (BO-02)

Когорта — месяц первого заказа клиента (`YYYY-MM`). Для когорты `m` и горизонта `h` месяцев:

```
LTV_m(h) = Σ margin_cents(заказы клиентов когорты m за [начало m; начало m + h мес.) ) / N_m
N_m = число клиентов в когорте
```

Средний LTV по каналу: те же когорты, но только клиенты с `first_channel_id = channel`; среднее взвешивается
по размеру когорт. Для среднего берутся только **завершённые** когорты (прошло не меньше `h` месяцев от начала
когорты). Незавершённые показываются отдельно с пометкой «неполные данные» и не попадают в средние и в LTV:CAC.

Горизонты: 3, 6, 12 месяцев. По умолчанию — 12.

Маржа заказа: `orders.margin_cents` (выручка минус себестоимость и доставка), задаётся при импорте/сиде,
не вычисляется в рантайме из процента.

Краевые случаи:
- `N_m = 0` → когорта отсутствует.
- Нет ни одной завершённой когорты → `ltv = null`, статус «недостаточно истории».
- Возвраты/отмены в MVP не моделируются; заказы считаются состоявшимися.

Пример: когорта 2026-01, 120 клиентов, маржа за 12 месяцев 1 440 000 c → LTV12 = 12 000 c = 120,00 BYN.

## 3. ROMI, payback, LTV:CAC (BO-03)

### 3.1. Атрибуция выручки

Окно атрибуции — 30 дней до момента заказа. Для каждого заказа берутся касания клиента
`occurred_at ∈ [order_at - 30 дней, order_at]`. Если касаний нет — используется канал привлечения клиента.

| Модель | Правило |
|---|---|
| `last_touch` (по умолчанию) | 100% выручки заказа — каналу последнего касания в окне |
| `first_touch` | 100% — каналу первого касания в окне |
| `linear` | выручка делится поровну между всеми касаниями окна (каждое касание — равная доля) |

Доли хранятся как рациональные и суммируются до копейки: остаток от деления распределяется по касаниям
в порядке времени (первое получает +1 копейку), чтобы `Σ attributed = order.revenue` точно.

`revenue_channel` — сумма атрибутированной выручки за период по заказам с `occurred_at ∈ [from, to]`.

### 3.2. ROMI

```
ROMI_channel = (revenue_channel - spend_channel) / spend_channel * 100%
```

- `spend = 0` → `romi = null` (не «бесконечность»).
- Отрицательная выручка невозможна (CHECK в БД).
- В интерфейсе показывается со знаком и одним знаком после запятой; в API — число с 2 знаками.

### 3.3. Payback

```
monthly_margin_per_customer = LTV_channel(12) / 12
payback_months = CAC_channel / monthly_margin_per_customer
```

Если `LTV` или `CAC` = `null`, либо `monthly_margin = 0` → `payback = null`.
Payback — приближение (средняя маржа равномерна по месяцам); в UI подпись «оценка».

### 3.4. LTV:CAC и статус здоровья

```
ratio = LTV_channel(12) / CAC_channel
```

| Статус | Условие |
|---|---|
| `healthy` | `ratio ≥ 3` и `payback ≤ 12` |
| `watch` | `1 ≤ ratio < 3` или `12 < payback ≤ 18` |
| `risk` | `ratio < 1` или `payback > 18` или `romi < 0` |
| `no_data` | не хватает CAC/LTV/ROMI |

Пороги — константы `src/config/metrics.js`, меняются в одном месте. Приоритет статусов: `no_data` → `risk` →
`watch` → `healthy`.

## 4. Рейтинг каналов (BO-04)

Критерии и веса по умолчанию: CAC 0.30 (меньше — лучше), ROMI 0.30, LTV:CAC 0.25, новые клиенты 0.15.
Веса приходят из UI, сумма нормируется к 1; отрицательные запрещены.

```
norm(x) = (x - min) / (max - min), при max == min → 1
cac_score = 1 - norm(CAC)
score = 100 * (0.30*cac_score + 0.30*norm(ROMI) + 0.25*norm(LTV:CAC) + 0.15*norm(new_customers))
```

Каналы со статусом `no_data` исключаются из рейтинга и показываются отдельным блоком «недостаточно данных».
В UI рядом со score — вклад каждого критерия (стек-бар), чтобы решение было объяснимым.

## 5. Когортный анализ (BO-06)

Смещение `k` — число полных месяцев от месяца первого заказа.
`active_k` — клиенты когорты, у которых есть хотя бы один заказ в месяц `m + k`.

```
retention_k = active_k / N_m * 100%
cum_ltv_k = Σ margin_cents(заказы за месяцы 0..k) / N_m
```

Матрица: строки — когорты, столбцы — `k = 0..11`. Ячейки без данных — пустые, не нули. Для когорт, где
`k` ещё не наступил, ячейка не заполняется.

## 6. Сценарии и оптимизация бюджета (BO-07, BO-08)

### 6.1. Кривая насыщения

По недельным данным канала за последние 26 недель подгоняется:

```
conversions(b) = K * (1 - exp(-b / S))
```

`b` — расход за неделю, `K` — потолок конверсий, `S` — масштаб насыщения. Подгонка детерминированная:
сетка `K ∈ [1.05*max(q), 4*max(q)]` (60 шагов), `S ∈ [0.33*mean(b), 3*max(b)]` (60 шагов, логарифмически),
минимизация SSE. Требуется минимум 8 недель с `b > 0`; иначе — линейная модель `q = CPA_const * b` с пометкой.

Качество: `R² = 1 - SSE/SST`. При `R² < 0.3` в UI показывается предупреждение «кривая ненадёжна».

### 6.2. Оптимальное распределение

Максимизируется сумма конверсий при фиксированном бюджете `B`:

```
max Σ K_i (1 - exp(-b_i / S_i)),  Σ b_i = B, b_i ≥ 0
```

Решение через KKT: предельная отдача `K_i/S_i * exp(-b_i/S_i) = λ`, откуда

```
b_i(λ) = S_i * ln(K_i / (S_i * λ)), если λ < K_i/S_i, иначе 0
```

`λ` находится бисекцией на `(0, max(K_i/S_i)]` за 80 итераций: `Σ b_i(λ)` строго убывает по λ и стремится к
бесконечности при λ→0, поэтому произвольного нижнего порога λ нет. Ошибка валидации возвращается, только если нет
каналов с валидной кривой или `B` меньше `1 копейка × число каналов в оптимизации`.

Бюджет переводится в копейки: доли `b_i` округляются вниз, остаток раздаётся каналам с наибольшей дробной частью
(largest remainder) до точной суммы `Σ spendCents = B`; канал всегда получает не меньше 1 копейки. Непрерывные доли
монотонны по `B`, но копеечное округление может переставить одну копейку между каналами (парадокс Алабамы), поэтому
гарантия для копеечных сумм — **монотонность с допуском 1 копейка**: при росте `B` ни одна аллокация не
уменьшается больше чем на 1 копейку. Это фиксируется пошаговым свипом в тестах оптимизатора.

### 6.3. Прогноз сценария

```
new_customers_i = conversions_i(b_i)
CAC_i = b_i / new_customers_i
revenue12_i = new_customers_i * LTV12_i
ROMI12_i = (revenue12_i - b_i*52) / (b_i*52) * 100%   // b_i — недельный бюджет
```

В UI явно подписано: «прогноз на 12 месяцев, при текущем LTV». Сценарий сохраняется с параметрами и результатом;
пересчёт при изменении входов.

Ограничение честности: если новый суммарный бюджет больше 2× фактического, показывается предупреждение
об экстраполяции. Каналы без валидной кривой в оптимизации не участвуют.

## 7. Алерты (BO-09)

Окна: последние 4 полные недели (`now`) и предыдущие 4 недели (`prev`) относительно data anchor (§0.1),
отчётная дата — понедельник.

| Правило | Условие | Severity |
|---|---|---|
| `cac_spike` | `CAC_now > CAC_prev * 1.2` | warning |
| `cac_spike` | `CAC_now > CAC_prev * 1.5` | critical |
| `romi_below_target` | `ROMI_now < target_romi` | warning |
| `romi_negative` | `ROMI_now < 0` | critical |
| `payback_long` | `payback > 12` | warning |
| `ltv_cac_low` | `LTV:CAC < 1` | critical |

Требования: в обоих окнах есть расход и новые клиенты; иначе правило не срабатывает (не спамим ложными алертами).
Дедупликация: `UNIQUE(channel_id, rule, period_start)`; повторный пересчёт обновляет значение, а не плодит записи.
Статусы: `active`, `resolved`, `dismissed` (последний — только аналитик/админ, с записью в аудит).
Пересчёт: кнопка «Пересчитать» + автоматически при открытии страницы алертов (не чаще раза в час на пользователя).

## 8. Импорт и экспорт (BO-11, BO-12)

CSV, разделитель `;`, кодировка UTF-8 (BOM допускается), десятичная запятая или точка.
Типы файлов: `daily_stats`, `customers`, `touchpoints`, `orders` (шаблоны скачиваются со страницы импорта).

| Тип | Обязательные колонки | Ключ дедупликации |
|---|---|---|
| `daily_stats` | `campaign_code;stat_date;impressions;clicks;leads;spend` | `(campaign_id, stat_date)` — обновление |
| `customers` | `external_id;first_channel_code;first_campaign_code;first_order_at` | `external_id` — пропуск |
| `touchpoints` | `customer_external_id;channel_code;campaign_code;occurred_at;kind` | `(customer_external_id, occurred_at, channel_code)` — пропуск |
| `orders` | `external_id;customer_external_id;campaign_code;occurred_at;revenue;margin` | `external_id` — пропуск |

Связность при импорте:
- `customers` создаёт клиента и фиксирует канал/кампанию привлечения; заказ без существующего клиента — ошибка строки;
- `touchpoints` дополняют историю касаний; если у клиента ещё нет `first_channel_id`, он берётся из самого раннего
  касания (канал привлечения не перезаписывается задним числом, если уже задан);
- касания и заказы обязаны ссылаться на существующие каналы/кампании, иначе строка отклоняется с понятной ошибкой;
- все суммы — в BYN, маржа не может быть отрицательной и не может превышать выручку.

Правила:
- обязательные колонки проверяются Zod-схемой, лишние игнорируются с предупреждением;
- каждая строка валидируется; ошибки собираются с номером строки и причиной, валидные строки не применяются,
  если ошибок больше 10% (атомарность пакета, транзакция);
- дубликаты: `daily_stats` — по `(campaign_id, stat_date)` (обновление), `customers` — по `external_id`
  (пропуск с отметкой «дубль»), `orders` — по `external_id` заказа (пропуск);
- лимиты: 2 МБ, 10 000 строк, имя файла санитизируется;
- результат импорта — `import_batches` + `errors` JSONB, ссылка на отчёт.

Экспорт: CSV с теми же разделителями, `Content-Disposition` с датой, только текущие фильтры; экспорт пишется в аудит.

## 9. Форматирование BYN

- Внутри — копейки. На границе API — копейки + `currency: "BYN"`.
- Полный формат: `1 234,56` + графический знак НБРБ (`<span class="byn">BYN</span>`, шрифт `nbrb`).
- Компактный формат для осей: `12,4 тыс.`, `1,2 млн`; знак в подписи оси, не в каждой точке.
- Ввод: принимает `1 234,56`, `1234.56`, `1234,5`; пробелы и знак валюты отбрасываются, отрицательные — ошибка.
- `tabular-nums` для всех числовых колонок и KPI.
